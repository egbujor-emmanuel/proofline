Your tests passed. Did your promises survive?

Kane proves a test passes. Proofline proves a specific product promise still holds after a specific code change — and tells you which promise the change put at risk.

Change in, decision out

Four steps. Kane owns execution and evidence. Proofline owns the two questions Kane has no concept of: which requirement a diff endangers, and whether the resulting evidence is strong enough to ship on.

It caught a real regression

Not a staged one. Two lines were changed in the subscription service so the upgrade endpoint still returned {"plan":"pro"} — but never persisted it. The API looked correct. The UI showed success. Only a fresh read revealed the truth.

app/server/services/subscriptionService.js
function upgradeToPro() {
  const account = readAccount();
-  account.plan = 'pro';
-  return writeAccount(account);
+  const upgraded = { ...account, plan: 'pro' };
+  return upgraded;
}

Proofline, before the fix

AC-1 · requirement broken

Mapped to AC-1 first, with high confidence, ran only the tests covering it, and blocked the change.

Proofline, after the fix

AC-1 · proven

Same criterion, same targeted verification, clean run. The promise is kept, and there's evidence to say so.

“The upgrade appeared to succeed earlier, but the app did not actually save the new plan. When the dashboard was loaded again from the server, the account was still treated as Free.” Kane's own verdict — application_issue / functional_defect / major · corroborated by GET /api/pro-feature → 403

The criterion at stake, in the requirements' own words: “After a successful upgrade request, the account's persisted plan changes from free to pro.” Extracted from the PRD by Kane · verified against a real browser

Six ways evidence can fail you

Every one of these was discovered by running this against real code — not designed on a whiteboard. Proofline never reports a promise as proven when the proof is weaker than it looks.

StateWhat it meansDecision
proven An explicit runtime check targets this exact criterion, on a clean run.The only state that can ship. ship
proven on a healed run The check passed — but Kane silently re-authored the test mid-run.Observed for real: a healed run rewrote a test into checking optimistic UI state instead of persisted state, reported PASS, and let a genuine regression through. review
not independently asserted A test claims this criterion and Kane counts it proven, but no assertion actually targets it.Kane's own strict and lenient coverage modes return identical numbers here — the distinction doesn't exist upstream. review
verification incomplete The test agent got stuck and never reached a verdict.Explicitly not evidence the product is broken — flattening these would make the tool lie. review
requirement broken The test completed and its assertion genuinely failed against the running app. block
no evidence No live test verifies this criterion at all.Silence is not proof. block

Run it

Needs Node 18+, Chrome, and a TestMu AI account. The target repo must already have its requirements in Kane's graph — Proofline verifies against a project's existing corpus, it doesn't invent one. 

# Kane, authenticated
npm install -g @testmuai/kane-cli && kane-cli login --oauth

# this repo, and the app it verifies (leave this running)
git clone https://github.com/egbujor-emmanuel/proofline
cd proofline/app && npm install && npm start
# in a second terminal
cd proofline/proofline-cli

# what would this change put at risk? (free, no Kane credits)
node bin/proofline.js --repo .. --dry-run --ref HEAD~1

# verify it for real, and write a shareable report
node bin/proofline.js --repo .. --ref HEAD~1 --report ../proof-report.html

The reasoning layer works with either an ANTHROPIC_API_KEY or the claude CLI. With neither, Proofline still runs on its deterministic ranking and says so plainly rather than faking a score.
